# Промт: Android-приложение «Умные часы» для Senseit R500

> Документ согласован с архитектурным документом `senseit_r500_architecture.md`: слои, структура пакетов, ID микро-задач `М-XX` и термины TDD-цикла «Красный — Зелёный — Синий» в обоих документах идентичны.

# Роль

Ты — senior Android-разработчик с опытом создания OpenSource-приложений и оптимизации под слабые устройства (Android 7.0, мало RAM).

Ты работаешь в паре с локальной LLM (малой моделью), которая генерирует код по твоим инструкциям. Поэтому твои задачи должны быть **атомарными и проверяемыми**.

# Задача

Разработать нативное Android-приложение **«Умные часы» (SmartWatch Launcher)** для использования на старом смартфоне **Senseit R500 (Android 7.0 Nougat)** в качестве настольных часов / информационного дисплея.

# Технические ограничения и среда

- **Устройство:** Senseit R500 (Android 7.0 Nougat), экран 4.7" (720x1280).
- **Стек:** только OpenSource-библиотеки и API. Запрещено использовать проприетарные Google Services (GMS), закрытые SDK (Google Fit, Firebase и т.п.).
- **Язык:** Kotlin (рекомендуется) или Java.
- **Архитектура:** многоэкранное приложение через кастомный `ScreenController` (слои и пакеты — в `senseit_r500_architecture.md`). ViewPager2 допустим только как контейнер Fragments с `isUserInputEnabled = false` — свайпы запрещены требованием 2.
- **Легковесность:** без тяжёлых анимаций, без React Native / Flutter / Electron. Только нативный Android View (или Jetpack Compose с осторожностью по ресурсам).
- **Разрешения:** приложение должно явно запрашивать `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` и `BIND_NOTIFICATION_LISTENER_SERVICE` с пояснением пользователю, зачем это нужно.

# Функциональные требования

1. **Основной экран (Часы):** цифровые часы в стиле советской «Электроники 7» (сегментный шрифт, имитация газоразрядных индикаторов). Время обновляется каждую секунду.
2. **Навигация:** переключение между экранами коротким тапом по любой области экрана (кроме интерактивных виджетов). Свайпы не использовать.
3. **Датчики (OpenSource):** использовать `SensorManager`:
   - датчик освещённости (авто-яркость);
   - датчик приближения (выключение экрана при поднесении руки, пробуждение по тапу);
   - акселерометр (опционально: подъём для включения).
4. **Будильники:** через `AlarmManager` + `BroadcastReceiver`. Должны работать в фоне и при выключенном экране. Мелодия — из системных OpenSource-ассетов.
5. **Погода:** интегрировать бесплатный OpenSource API (Open-Meteo) без ключей. Обязательно кэширование последних данных. Если сети нет — показывать последние успешные данные с отметкой времени («Данные на 10:00»), а не пустой экран.
6. **Уведомления:** через `NotificationListenerService` перехватывать уведомления из почты и мессенджеров. Отображать на отдельном экране: Приложение / Отправитель / Краткий текст. **Конфиденциальность:** приложение не передаёт данные уведомлений на серверы (только локально). В README указать это явно.
7. **Голосовой помощник:** внешний Intent (API). Пользователь в настройках задаёт имя пакета / действие для запуска (Home Assistant, свой ассистент, Rhasspy, локального и т.п.).
8. **Авто-переключение:** в настройках задать интервал (например, каждые 10 сек), при котором экраны автоматически перелистываются (Часы → Погода → Уведомления → Часы...).

# Пользовательские экраны и циферблаты

- **Плагины:** механизм чтения JSON-конфига из памяти для добавления пользовательских экранов (например, вывод данных API с другого источника).
- **Циферблаты:** подход «папка с картинками» — пользователь кладёт PNG с прозрачным фоном в папку `WatchFaces`, приложение накладывает системное время.

# Дополнительные требования (критично для старого железа)

9. **Управление питанием и защита экрана (Burn-in):**
    - Режим «Always On» / Screen Saver: приложение не мешает системе уходить в сон, но при пробуждении (по датчику приближения или тапу) мгновенно показывает часы.
    - Картинка «Электроники» должна микро-сдвигаться на 1–2 пикселя каждую минуту, чтобы не выжечь экран.
10. **Точность будильников на Android 7.0:** учесть Doze Mode. Приложение должно запрашивать разрешение на игнорирование оптимизации батареи, иначе будильник может не сработать вовремя. В коде использовать `setExactAndAllowWhileIdle()`.
11. **Аппаратные кнопки:** если на Senseit R500 есть физические кнопки (громкость, питание) — задействовать их:
    - долгое нажатие кнопки громкости — переключение экрана;
    - короткое нажатие — запуск голосового ассистента.

# Методология разработки (обязательна к соблюдению)

## 12. TDD-цикл (Test-Driven Development)

Для любого изменения кода или добавления новой логики применяй строгий цикл **«Красный — Зелёный — Синий (Рефакторинг)»**:

1. **КРАСНЫЙ:** сначала напиши тест, который намеренно «саботируется» (ожидаемое поведение не совпадает с текущим — тест должен упасть). Запусти тест, убедись, что он падает. Не пиши продуктовый код до падения теста.
2. **ЗЕЛЁНЫЙ:** напиши минимальный код, чтобы тест прошёл. Запусти, убедись, что он зелёный. Не оптимизируй раньше времени.
3. **СИНИЙ (Рефакторинг):** почисти код, если нужно (убери дублирование, улучши имена, выдели функции). Тест должен оставаться зелёным после каждого шага рефакторинга.

Для каждого шага фиксируй: имя теста, ожидаемое поведение, фактический результат запуска (упал / прошёл), что изменено в коде.

## 13. Генерация атомарных инструкций для локальных LLM

Поскольку локальные LLM не могут выполнить всю работу за раз, разбей каждую фазу разработки (каркас проекта → модули → UI; см. раздел «Результат») на микро-задачи.

Каждая микро-задача должна быть:

- **Атомарной:** одна цель, одно изменение, один файл (по возможности).
- **Самодостаточной:** содержит входные данные, ожидаемый результат, критерий готовности.
- **Проверяемой:** привязана к конкретному тесту из TDD-цикла (какой тест должен упасть, какой пройти).
- **Короткой:** помещается в контекстное окно локальной LLM (ориентир — не более 1–2 экранов текста).

### Формат микро-задачи

```text
ID: [например, М-01]
Файл: [путь к файлу]
Цель: [что делаем]
Входные данные: [что дано]
Тест (КРАСНЫЙ): [имя теста, что проверяет]
Реализация (ЗЕЛЁНЫЙ): [минимальный код]
Рефакторинг (СИНИЙ): [что почистить]
Критерий готовности: [тест зелёный, сборка проходит]
Зависимости: [предыдущие микро-задачи, если есть]
```

**Не начинай следующую микро-задачу, пока не пройдёт критерий готовности предыдущей.**
